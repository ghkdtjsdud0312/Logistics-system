# SCOPE

## Must Have

- 기준정보: 상품, 창고·구역·위치, 차량, 기사
- 입고·적치 및 재고 현황(현재/예약/가용)
- 주문 생성·조회·상세(진행 타임라인, 이벤트 이력)
- 피킹, 포장, 상차(Shipment 생성)
- 배차 등록, 배송 시작, 배송현황, 배송 완료/실패
- 반품(회수 흐름, 재고 복구)
- 감사로그(모든 상태 변경 기록·검색)
- 대시보드(오늘의 현황, 진행 현황, 차량 배송 현황, 최근 이벤트)와 SSE 실시간 갱신
- Kafka 상태 변경 이벤트, Redis 대시보드 캐시
- 핵심 API와 도메인 규칙 테스트, Docker Compose

## Should Have

- 샘플 데이터 시드와 `ORD-001` 데모 시나리오
- 재고 부족·과적 등 거부 사유의 명확한 오류 응답
- k6 대시보드 조회 캐시 ON/OFF 비교

## 제외 범위 (이번 개발 기간)

- 지도 → "나중에 추가" (3D 창고는 ADR-021, 스케줄 달력은 ADR-022로 2026-09-26에 구현)
- 경로 최적화(Nearest Neighbor, 2-opt), 차량 후보 추천, 좌표/위경도
- 이상 탐지(anomaly) → 감사로그로 대체
- 주문 취소, 부분 피킹/부분 출고/부분 인도, 분할 적치, 재배송
- 로그인, 회원가입, 권한
- 결제, 회계, 다중 물류센터, MSA, ML

## 단순화 가정

- 고객은 별도 엔티티 없이 주문에 이름·주소·연락처를 내장한다.
- 박스는 포장 작업의 문자열 필드(`boxCode`)이며 별도 엔티티가 아니다.
- 주문 1건은 여러 상품 행을 가질 수 있고, Shipment는 주문 1건당 1개다.
- 배차 1건은 여러 Shipment를 묶고, 차량·기사는 한 번에 활성 배차 1건에만 배정된다.
- 적재량 검증은 중량(kg)만 사용한다(부피 제외).

## 시간 부족 시 축소 순서

1. k6 성능 비교 생략
2. 프런트 화면을 핵심 흐름(기준정보, 주문, 창고, 배송, 대시보드)만 구현하고 반품·감사로그 화면은 목록만 구현
3. Redis 캐시 대상을 대시보드 요약 한 종류로 제한

주문 → 배송 완료 흐름, 상태 전이 규칙, 재고 정합성, 감사로그는 축소하지 않는다.
