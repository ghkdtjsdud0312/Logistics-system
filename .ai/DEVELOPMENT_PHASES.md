# 3-DAY DEVELOPMENT PHASES

기간: 2026-09-25(금) ~ 09-27(일). 하루 종료 시 반드시 실행 가능한 상태와 데모 증거를 남긴다. 다음 날 기능을 당겨 범위를 넓히지 않는다. (기존 7일 계획은 ADR-012로 대체)

## 우선순위 (Phase)

1. **Phase 1 — 핵심 업무**: 기준정보 → 입고/적치 → 재고 → 주문 → 피킹 → 포장 → 상차 → 배차 → 배송 → 배송완료
2. **Phase 2 — 예외 처리**: 배송실패 → 반품/회수
3. **Phase 3 — 시스템 기능**: 감사로그
4. **Phase 4 — 보여주기 기능**: 대시보드 → SSE 실시간 갱신
5. **나중에 추가**: 스케줄(달력), 지도, 3D 창고

## Day 1 (금) — 문서 확정, 기준정보, 입고·재고

- 문서 개정 승인, API 스펙 확정
- 기존 폐기 대상 코드 정리(승인 후), 공통 상태 변경 이벤트 발행 기반
- 기준정보(상품, 창고·구역·위치, 차량·기사)
- 입고·적치와 재고(현재/예약/가용)
- 프런트: 레이아웃/라우팅, 기준정보·재고·입고 화면

종료 증거: 입고 100개 적치 후 재고 현황에 현재 100 / 예약 0 / 가용 100 표시.

## Day 2 (토) — 주문부터 배송까지 (`ORD-001` 관통)

- 주문 생성과 재고 예약, 출고 지시
- 피킹·포장
- 상차(Shipment), 배차 등록·시작
- 배송현황, 배송완료·실패
- 프런트: 주문, 피킹·포장, 배송관리 화면

종료 증거: `ORD-001`이 주문접수에서 배송완료까지 API/화면으로 이동하고 재고 수량이 규칙대로 변한다.

## Day 3 (일) — 반품, 감사로그, 대시보드, 마무리

- 반품 흐름과 재고 복구
- Kafka AuditConsumer와 감사로그 조회
- 대시보드 요약(Redis 캐시), SSE 실시간 갱신
- 프런트: 반품, 감사로그, 대시보드
- E2E 검증, README, 데모 스크립트 (여유 시 k6)

종료 증거: 배송완료 한 번으로 감사로그 기록, 캐시 무효화, 대시보드 SSE 갱신을 확인한다.

## 중단 기준

각 Day의 필수 증거가 없으면 다음 기술을 추가하지 않는다. Kafka가 불안정하면 동기 업무 흐름과 테스트를 보존하고 실패 원인과 미완료 범위를 명시한다. 시간이 부족하면 `SCOPE.md`의 축소 순서를 따른다.
