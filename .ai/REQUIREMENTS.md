# REQUIREMENTS

## 핵심 업무 흐름 (End-to-End)

입고 → 검수 → 입고 완료 → 출고 계획 → 차량/기사 배차 → 배송 경로 최적화 → 상차 → 출발 → 배송 → 배송 완료

## 입고

- `REQ-001` 거래처 또는 운영자는 입고 예정 정보를 등록할 수 있다.
- `REQ-002` 운영자는 실제 수량·중량·부피를 검수하고 입고를 완료할 수 있다.
- `REQ-003` 입고 상태는 `EXPECTED → INSPECTING → COMPLETED` 순서만 허용한다.

## 출고

- `REQ-004` 입고 완료된 가용 물량만 출고 계획에 포함할 수 있다.
- `REQ-005` 출고 계획은 배송지, 우선순위, 희망 배송일, 총 중량·부피를 계산한다.
- `REQ-006` 확정된 배차에 포함된 출고 물량을 다른 활성 배차에 중복 할당할 수 없다.

## 차량·기사·배차

- `REQ-007` 차량은 최대 중량·부피와 운행 상태를 가진다.
- `REQ-008` 기사는 가용 상태와 중복 일정 여부를 가진다.
- `REQ-009` 시스템은 적재량과 가용 상태를 만족하는 차량 후보를 반환한다.
- `REQ-010` 담당자는 후보 차량과 기사를 선택해 배차를 확정한다.
- `REQ-011` 중량 또는 부피가 한도를 초과하면 배차를 거부하고 이유를 반환한다.

## 경로

- `REQ-012` 확정 배차의 출발지와 배송지 좌표로 초기 방문 순서를 계산한다.
- `REQ-013` 2-opt로 초기 경로를 개선하고 전후 거리·개선율을 저장한다.
- `REQ-014` 모든 배송지는 정확히 한 번 포함되어야 하며 출발지는 첫 노드다.

## 배송·관제

- `REQ-015` 배차 상태는 정의된 상태 머신을 따라 변경된다.
- `REQ-016` 모든 상태 변경은 변경 시각과 행위자, 설명을 이력으로 남긴다.
- `REQ-017` 주요 상태 변경은 Kafka 이벤트로 발행한다.
- `REQ-018` 관리자 클라이언트는 SSE로 상태 변경 이벤트를 수신한다.
- `REQ-019` 과적, 상태 역전, 기사 중복, 장시간 정체를 이상으로 기록한다.

## 성능·운영

- `REQ-020` 배차/배송 상세 조회에 Redis 캐시와 TTL을 적용한다.
- `REQ-021` 상태 변경 시 관련 캐시를 무효화한다.
- `REQ-022` k6로 캐시 적용 전후 평균, p95, 처리량, 오류율을 비교한다.
- `REQ-023` 핵심 서비스는 Docker Compose로 실행 가능해야 한다.
- `REQ-024` API 오류는 일관된 오류 코드와 추적 ID를 반환한다.

## 비기능 요구사항

- `NFR-001` 단일 API 요청의 DB 변경은 트랜잭션 경계를 명확히 한다.
- `NFR-002` 생성 API는 `Idempotency-Key`를 지원하거나 중복 방지 키를 가진다.
- `NFR-003` 동일 이벤트의 재처리는 최종 상태를 중복 생성하지 않는다.
- `NFR-004` 테스트는 시스템 시간과 난수를 주입 가능하게 만든다.
- `NFR-005` 로그에는 추적 ID와 업무 식별자를 포함하되 개인정보는 마스킹한다.
