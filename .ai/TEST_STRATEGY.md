# TEST STRATEGY

## 테스트 피라미드

- Domain unit: 상태 머신, 재고 계산, 수량 규칙, 적재량 검증
- Application unit/integration: 유스케이스 orchestration, 도메인 간 협력, 예외
- Repository/API integration: 요청 검증, 상태 코드, 오류 계약 (테스트 DB는 기존 H2 관행, PostgreSQL 전용 기능은 사용하지 않는다)
- Messaging: Consumer 멱등성
- E2E smoke: `ORD-001` 주문부터 배송완료까지, 실패→반품 시나리오
- Performance(선택): k6 대시보드 조회 캐시 OFF/ON 비교

## 실제 구성 (구현 결과)

- 도메인 단위·서비스·API 통합 테스트는 H2(`test` 프로파일)로 실행한다. 새 인프라 의존성 없이 재현되도록 Kafka 발행·Consumer는 끄고 대시보드 캐시는 인메모리 구현을 쓴다.
- 커밋이 필요한 동시성 테스트(동시 주문, 동시 배차)는 트랜잭션 없이 실행하고 `TestData.clear()`로 정리한다.
- Redis 장애 폴백과 Consumer의 캐시 무효화·SSE 전송은 Mockito로 검증하고, 실제 Kafka·Redis·SSE 연동은 로컬 인프라에서 수동 검증했다(감사로그 기록, 캐시 무효화, Redis 중지 시 200 응답).
- E2E: `OrderJourneyE2ETest`가 `ORD-001` 성공 흐름과 배송 실패 → 반품 → 재고 복구 흐름을 API만으로 검증한다.
- k6 성능 비교(대시보드 요약 캐시 OFF/ON)는 `k6/README.md`에 결과를 기록했다.
- 미실시: 프런트 자동 테스트, 브라우저 자동화.

## 필수 케이스

### 재고·입고
- 적치완료 시 위치 재고가 입고수량만큼 증가하고 상태가 적치완료가 된다.
- 입고완료 전 적치, 이미 적치된 입고의 재적치를 거부한다.
- 가용재고 = 현재재고 − 예약재고, 음수 재고 불가.

### 주문·피킹·포장
- 가용재고 이내 주문은 예약 성공, 초과 주문은 `INSUFFICIENT_STOCK`이며 예약이 남지 않는다.
- 다중 위치에 걸친 예약 배분과 피킹 작업 생성.
- 피킹수량 ≠ 요청수량 거부, 초과 거부, 완료 시 현재·예약 동시 차감.
- 모든 피킹 완료 후에만 포장 작업 생성과 상태 전이.
- 동시 주문 요청에서 가용재고를 초과 예약하지 않는다.

### 상차·배차
- 포장완료 아닌 주문 상차 거부.
- 적재량 경계값(같음 통과, 초과 거부).
- 가용하지 않은 차량·기사, 활성 배차 중인 차량·기사, 이미 배차된 Shipment 거부.
- 배차 등록 실패 시 부분 데이터 없음. 배송 시작 전 취소 시 상태 원복.

### 배송·반품
- 인도수량 불일치 거부, 완료 후 재처리 거부.
- 모든 Shipment 종결 시 배차 자동 완료와 차량·기사 복귀.
- 실패 시 반품 1건 자동 생성, 반품 상태 전이 순서.
- 파손이 아닌 반품입고는 재고 복구, 파손은 복구 없음.

### 상태·이벤트·캐시
- 주문 상태 모든 허용 전이와 주요 금지 전이, 종결 상태 변경 차단.
- 상태 변경 시 이벤트 발행, 같은 eventId 중복 소비 시 감사로그 1건.
- 상태 변경 후 대시보드 캐시 무효화, Redis 장애 시 DB 폴백(`CacheErrorHandler` 단위 테스트, ADR-010).
- SSE 브로드캐스트와 전송 실패 emitter 제거.

## k6 기준 (선택)

시나리오 `GET /api/dashboard/summary`, 20 → 100 → 300 VU, 캐시 OFF/ON 각각 워밍업 후 측정. 평균, p95, req/s, 오류율을 원시 결과와 환경과 함께 기록하고 성능 향상을 미리 단정하지 않는다.
