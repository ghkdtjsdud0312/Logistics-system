# Day 4 — 배송 경로 최적화와 상태 관리

## 1. 오늘의 목표

확정된 배차의 배송지 방문 순서를 계산하고, 상차부터 배송 완료까지의 상태를 상태 머신으로 관리한다. 경로는 실제 도로 최적화가 아닌 좌표 기반 근사 알고리즘임을 코드와 화면에서 명확히 한다.

## 2. 관련 범위

- 요구사항: `REQ-012`~`REQ-016`
- 작업: `TASK-007`, `TASK-008`
- 선행조건: 확정 Dispatch와 유효한 배송지 좌표
- 범위 밖: 교통량, 도로망, 시간창 VRP, 실제 GPS

## 3. 경로 계산 모델

### 거리

데모 평면 좌표라면 유클리드 거리를 사용한다. 실제 위·경도라면 Haversine을 사용한다. 한 프로젝트 안에서 두 모델을 혼용하지 않고 거리 단위를 응답에 명시한다.

### 초기 경로

허브에서 시작해 아직 방문하지 않은 배송지 중 가장 가까운 곳을 선택하는 Nearest Neighbor를 사용한다. 거리가 같으면 OutboundPlan ID 등 고정된 tie-breaker로 결정한다.

### 경로 개선

2-opt로 두 간선을 교환하면서 총 거리가 감소하는 경우만 반영한다. 반복 횟수 상한을 두고 다음을 보장한다.

- 모든 배송지가 정확히 한 번 등장
- 허브가 첫 노드
- 최적화 거리가 초기 거리보다 증가하지 않음
- 동일 입력에 동일 결과

## 4. 저장 데이터

- 알고리즘 이름과 버전
- 초기 거리, 최적화 거리, 개선율
- RouteStop의 순서, 이전 지점 거리, 상태
- 계산 시각과 입력 배차 version

배차 물량이 변경되면 기존 경로는 무효로 간주한다.

## 5. 배송 상태

Dispatch는 `CONFIRMED → LOADED → IN_TRANSIT → COMPLETED`를 따른다. RouteStop은 `PENDING → ARRIVED → DELIVERED`를 따른다.

- 모든 Stop이 DELIVERED일 때만 Dispatch를 COMPLETED로 만들 수 있다.
- COMPLETED 이후 상태 변경은 거부한다.
- 상태 변경마다 행위자, 이전/이후 상태, 시각, 설명을 이력으로 저장한다.

## 6. API 범위

- `POST /api/v1/dispatches/{id}/route/optimize`
- `PATCH /api/v1/dispatches/{id}/status`
- `PATCH /api/v1/dispatches/{id}/stops/{stopId}`
- 경로와 이력이 포함된 배차 상세 조회

## 7. 테스트

### 알고리즘

- 배송지 0개/1개/여러 개
- 알려진 좌표 세트의 거리
- 모든 노드 유일성과 누락 없음
- tie-breaker 결정성
- 2-opt 결과가 초기 결과보다 길지 않음
- 반복 상한과 실행시간

### 상태

- 모든 허용 전이
- `CONFIRMED → IN_TRANSIT` 등 건너뛰기 차단
- COMPLETED 역전 차단
- Stop 미완료 상태에서 Dispatch 완료 차단
- 낙관적 잠금 충돌
- 상태 변경 이력의 정확성

## 8. 산출물

- 순수 함수 형태의 거리·Nearest Neighbor·2-opt 모듈
- Route/RouteStop 저장 구조
- Dispatch와 Stop 상태 전이
- 이력 조회와 OpenAPI 예시
- 알고리즘/도메인 테스트
