# Day 6 — 운영 화면·통합 시나리오·성능 검증

## 1. 오늘의 목표

물류 담당자가 핵심 업무 흐름을 시연할 수 있는 화면을 만들고, 입고부터 배송 완료까지 통합 시나리오를 검증한다. Redis의 효과는 k6로 같은 조건에서 측정한다.

## 2. 관련 범위

- 요구사항: `REQ-001`~`REQ-024`
- 작업: `TASK-012`, `TASK-013`
- 선행조건: API와 이벤트 계약 고정
- 범위 밖: 디자인 시스템, 실제 지도, 모바일 최적화, 운영 규모 성능 주장

## 3. 화면 우선순위

### 필수 화면

1. 물류 대시보드: 입고·출고·배차·배송·이상 요약
2. 입고/출고 관리: 검수와 출고 계획 진행
3. 배차/경로 관리: 후보 비교, 배차 확정, 경로 전후 비교
4. 실시간 관제: 차량별 진행률과 SSE 이벤트 피드

시간이 부족하면 이상 목록을 관제 화면의 패널로 합친다.

## 4. UX 기준

- 상태명과 오류 사유를 운영자가 이해할 수 있는 한국어로 표시한다.
- 과적 차량은 선택 후 실패시키기보다 후보 단계에서 제외 사유를 보여준다.
- 경로는 실제 지도 대신 방문 순서와 거리 표, 간단한 노드 시각화로 표현한다.
- 로딩, 빈 데이터, API 오류, SSE 재연결 상태를 구분한다.
- 데모 데이터 생성 방법을 제공한다.

## 5. 통합 시나리오

`DEMO_SCENARIO.md`의 12단계를 자동화 가능한 부분과 수동 시연으로 구분한다. 최소한 다음은 통합 테스트로 검증한다.

- 입고 완료 → 출고 계획 → 후보 조회 → 배차 확정
- 경로 최적화 → 상차 → 배송 시작 → 모든 Stop 완료 → Dispatch 완료
- 잘못된 전이의 오류와 이상 기록
- 이벤트 중복 처리 방지

## 6. k6 실험 설계

### 대상

`GET /api/v1/dispatches/{id}`의 Redis OFF/ON 비교

### 통제 변수

- 같은 머신, 데이터 크기, 애플리케이션 설정
- 같은 VU 단계와 실행 시간
- 각 실험 전 동일한 워밍업
- 캐시 ON 실험은 hit ratio 기록

### 부하 단계

- 20 VU: 기능 안정성
- 100 VU: 일반 부하
- 300 VU: 병목 관찰

### 기록

- 평균 응답시간, p95, req/s, 오류율
- DB query count 또는 관련 지표
- CPU/메모리 등 측정 가능한 환경 정보
- 캐시 hit/miss

결과가 기대와 다르더라도 숨기지 않고 원인을 분석한다.

## 7. Docker Compose 통합

Backend, Frontend, PostgreSQL, Redis, Kafka가 하나의 명령으로 실행되어야 한다. 서비스 기동 순서를 단순 `depends_on`에만 의존하지 않고 healthcheck와 재시도 정책을 사용한다.

## 8. 테스트

- 대표 통합 시나리오
- SSE 재연결과 중복 표시 방지
- Compose clean start smoke test
- k6 threshold와 결과 파일 생성

## 9. 산출물
