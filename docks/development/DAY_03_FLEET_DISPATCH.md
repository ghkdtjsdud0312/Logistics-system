# Day 3 — 차량·기사·배차 의사결정

## 1. 오늘의 목표

출고 계획의 물량과 배송 조건을 평가해 적합한 차량 후보를 제시하고, 담당자가 차량과 기사를 선택해 배차를 확정하도록 한다. 자동배차로 과장하지 않고 추천 근거와 제외 사유를 설명하는 운영 도구로 구현한다.

## 2. 관련 범위

- 요구사항: `REQ-006`~`REQ-011`
- 작업: `TASK-005`, `TASK-006`
- 선행조건: READY 상태 출고 계획과 정확한 중량·부피
- 범위 밖: 다중 차량에 물량 분할, 실제 기사 근무법규, 경로 계산

## 3. 도메인 구성

### Vehicle

- 차량번호, 차량 유형, 최대 중량, 최대 부피, 운행 상태
- 상태 예: `AVAILABLE`, `ASSIGNED`, `MAINTENANCE`, `INACTIVE`

### Driver

- 이름 또는 식별명, 가용 상태
- 같은 시간 구간에 활성 배차를 하나만 가질 수 있다.

### Dispatch

- 차량, 기사, 출고 계획 목록, 계획 시작시각
- 합산 중량·부피, 상태, 낙관적 잠금 version
- 생성 시 상태는 `CONFIRMED`로 두거나 DRAFT 저장 후 확정하는 한 방식을 일관되게 선택한다.

## 4. 차량 후보 산정

1. 출고 계획들의 총 중량과 부피를 계산한다.
2. AVAILABLE 차량을 조회한다.
3. 중량과 부피를 모두 충족하는지 판단한다.
4. 계획 시간에 다른 활성 배차가 있는 차량을 제외한다.
5. 잔여 적재율과 허브까지의 거리 패널티로 정렬한다.
6. 적합 차량에는 추천 근거, 부적합 차량에는 제외 사유를 제공한다.

후보 결과는 추천일 뿐 최종 배차는 담당자가 확정한다.

## 5. 핵심 불변식

- `totalWeight <= vehicle.maxWeight`
- `totalVolume <= vehicle.maxVolume`
- 차량과 기사는 해당 시간에 가용해야 한다.
- 출고 계획은 다른 활성 배차에 포함되어 있지 않아야 한다.
- 하나라도 위반하면 Dispatch 전체 생성을 롤백한다.

## 6. API 범위

- `POST /api/v1/dispatches/candidates`
- `POST /api/v1/dispatches`
- `GET /api/v1/dispatches/{id}` 기본 응답
- 차량·기사 가용 목록 조회

후보 API에는 차량별 적재 사용률과 제외 사유 코드가 포함되어야 한다.

## 7. 동시성 설계

같은 차량, 기사 또는 출고 계획을 두 요청이 동시에 확정하는 상황을 재현한다. DB 제약, 낙관적 잠금 또는 명시적 잠금을 조합해 하나만 성공하도록 한다. 애플리케이션 선행 조회만으로 보호하지 않는다.

## 8. 테스트

- 중량과 부피를 모두 만족하는 후보
- 중량은 만족하지만 부피 초과인 차량 제외
- MAINTENANCE 차량 제외
- 잔여 적재율에 따른 결정적 정렬
- 기사 일정 경계가 맞닿는 경우와 겹치는 경우
- 같은 출고 계획의 중복 배차 차단
- 동시 확정 요청 중 하나만 성공
- 실패 시 Dispatch와 연결 테이블에 잔여 데이터 없음

## 9. 산출물

- Vehicle, Driver, Dispatch 모델
- 후보 조회 서비스와 설명 가능한 결과
- 배차 확정 서비스와 동시성 보호
- 차량 유형별 샘플 데이터
- API/도메인/통합 테스트

## 10. 완료 기준

- [ ] 과적 차량을 선택해도 서버가 차단한다.
- [ ] 후보 목록에서 선택·제외 이유를 확인할 수 있다.
- [ ] 기사·차량·출고 계획의 중복 배정이 발생하지 않는다.
- [ ] 같은 입력의 후보 정렬이 재현 가능하다.
- [ ] 전체 테스트와 빌드가 통과한다.
