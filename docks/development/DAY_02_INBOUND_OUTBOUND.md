# Day 2 — 입고·검수·출고 계획

## 1. 오늘의 목표

물류센터에 들어오는 물량을 검수하고, 입고가 완료된 수량 범위 안에서 출고 계획을 생성하는 핵심 흐름을 완성한다. 단순 CRUD가 아니라 상태 전이와 가용 수량 불변식을 서버가 강제해야 한다.

## 2. 관련 범위

- 요구사항: `REQ-001`~`REQ-006`, `NFR-001`, `NFR-002`
- 작업: `TASK-003`, `TASK-004`
- 선행조건: Day 1 실행·마이그레이션·오류 규약 완료
- 범위 밖: 차량 추천, 기사 배정, 경로 알고리즘

## 3. 업무 흐름

```mermaid
flowchart LR
  A[입고 예정] --> B[검수 중]
  B --> C[입고 완료]
  C --> D[가용 수량 계산]
  D --> E[출고 계획 DRAFT]
  E --> F[출고 준비 READY]
```

## 4. 도메인 설계

### 4.1 Inbound

- 거래처, 예정일, 상태를 관리한다.
- InboundItem은 SKU, 예정 수량, 검수 수량, 단위 중량, 단위 부피를 가진다.
- `EXPECTED → INSPECTING → COMPLETED`만 허용한다.
- 완료 후 검수 수량과 단위값은 변경할 수 없다.

### 4.2 가용 수량

```text
availableQuantity = inspectedQuantity - activeOutboundAllocatedQuantity
```

가용 수량은 클라이언트 입력을 신뢰하지 않고 서버가 계산한다. 취소 또는 실패한 출고 계획의 수량 처리 정책을 명확히 테스트한다.

### 4.3 OutboundPlan

- 배송지 이름과 데모 좌표, 우선순위, 희망 배송일을 가진다.
- 여러 InboundItem에서 출고 수량을 할당할 수 있다.
- 총 중량과 총 부피는 수량과 단위값으로 계산한다.
- 완료되지 않은 입고와 가용 수량 초과 할당을 거부한다.

## 5. API 범위

- `POST /api/v1/inbounds`
- `PATCH /api/v1/inbounds/{id}/inspection`
- `POST /api/v1/inbounds/{id}/complete`
- `POST /api/v1/outbound-plans`
- 개발 확인을 위한 입고/출고 상세 조회

생성 API는 `Idempotency-Key` 또는 동등한 업무 중복 방지 키를 사용한다.

## 6. 트랜잭션과 동시성

- 검수, 입고 완료, 출고 계획 생성은 각각 명확한 트랜잭션으로 처리한다.
- 두 요청이 같은 가용 수량을 동시에 할당하지 못하도록 잠금 또는 원자적 검증 전략을 적용한다.
- 실패하면 출고 계획과 항목이 부분 저장되지 않아야 한다.

## 7. 테스트

### 정상

- 여러 품목을 포함한 입고 생성·검수·완료
- 입고 완료 수량 일부로 출고 계획 생성
- 중량과 부피 합계 계산

### 경계·오류

- 예정 수량과 검수 수량의 차이
- 0 또는 음수 수량 거부
- 완료 전 출고 할당 거부
- 가용 수량 정확히 전부 사용
- 가용 수량 1개 초과 거부
- 동일 멱등성 키 재요청 시 중복 방지
- 동시 할당 요청에서 총 할당량 초과 방지
- 잘못된 상태 전이와 완료 후 수정 차단

## 8. 산출물

- Inbound/InboundItem 도메인과 API
- OutboundPlan/OutboundItem 도메인과 API
- 가용 수량 계산 및 동시성 보호
- 요청/응답 DTO와 OpenAPI 예시
- 단위 및 통합 테스트
- 데모용 거래처·입고 데이터

## 9. 완료 기준

- [ ] 입고 예정부터 완료까지 정상 흐름이 동작한다.
- [ ] 출고 계획이 입고 완료와 가용 수량 규칙을 우회할 수 없다.
- [ ] 중복·동시 요청이 재고성 수량을 초과시키지 않는다.
- [ ] 모든 API 오류가 공통 계약을 따른다.
- [ ] 관련 테스트와 전체 빌드가 통과한다.
