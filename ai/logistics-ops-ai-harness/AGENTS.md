# AI Coding Agent Operating Contract

이 저장소에서 작업하는 모든 AI 에이전트는 이 문서를 최우선 프로젝트 지침으로 사용한다.

## 에이전트 기본 상태 (Context Memory)

- **아키텍처**: MSA가 아닌 Modular Monolith 구조다. 도메인 간 직접 참조를 금지하며 무조건 ID 참조 또는 이벤트로 격리한다.
- **인증 인프라**: Spring Security는 포함되어 있으나, 로그인 없이 접근 가능한 PermitAll 상태를 유지해야 한다.
- **데이터 흐름**: 배송 조회는 Redis(Cache-Aside), 상태 변경은 Kafka, 관제는 SSE를 사용한다.

## 시작 절차

1. 요청된 `TASK-ID`와 연결된 `REQ-ID`를 확인한다.
2. 관련 `.ai/*.md`와 현재 코드를 검색한다.
3. 요구사항, 도메인 불변식, API/DB 계약의 충돌 여부를 확인한다.
4. 수정 예상 파일, 영향 범위, 테스트 계획을 먼저 제시한다.
5. 승인 게이트가 아니면 작업을 계속하고, 승인 게이트이면 사용자 승인을 기다린다.

## 표준 작업 루프

`조사 → 계획 → 최소 구현 → 포맷/정적검사 → 단위·통합 테스트 → 빌드 → diff 검토 → 문서 갱신 → 결과 보고`

실패하면 원인을 근거로 수정하고 같은 검증을 다시 실행한다. 검증하지 않은 결과를 완료로 표시하지 않는다.

## 승인 게이트

다음 변경은 구현 전에 승인을 받는다.

- 새로운 런타임 라이브러리 또는 외부 서비스 추가
- 공개 API의 URI·요청·응답·상태 코드 변경
- DB 테이블·컬럼·제약조건·마이그레이션 변경
- Kafka 토픽/이벤트 스키마의 호환성 파괴
- 패키지 구조 또는 모듈 경계 변경
- Redis/Kafka/SSE 제거 또는 다른 기술로 교체
- 인증, 지도 API, MSA, Kubernetes, ML 등 범위 밖 기능 추가
- 요구사항 또는 테스트를 삭제·완화하여 실패를 숨기는 행위
- 소스 코드 파일이 300~400자(약 30~50줄)를 넘을 것으로 예상되는 경우 (분리 계획을 먼저 보고하고 승인받는다)

버그 수정, 기존 계약 내 구현, 테스트 보강, 문서 동기화는 승인 없이 계속할 수 있다.

## 금지 행동 (Anti-Patterns)

- 사용자의 컨펌 없이 다음 단계 코드를 마구잡이로 대량 생성하는 행위
- `pages/`나 Controller 내부에 TypeScript Interface·비즈니스 로직을 누산하는 행위
- 요구사항에 명시되지 않은 편의 기능(예: 회원가입, 유저 관리 등)을 임의로 추가하는 행위

## 구현 원칙

- Java 17과 Spring Boot 3.x를 사용한다.
- Controller는 입출력 변환과 위임만 담당한다.
- 핵심 규칙과 상태 전이는 Domain/Application 계층에 둔다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- 금액·중량·부피·거리 단위는 명시하고 부동소수점 오차를 피한다.
- 시간은 저장 시 UTC, 표시 시 사용자 시간대로 처리한다.
- 한 트랜잭션에서 DB 변경과 Kafka 발행의 원자성이 필요하면 Outbox를 우선 검토하되, 7일 MVP에서는 문서화된 단순화 정책을 따른다.
- 멱등성 키가 있는 생성 요청은 같은 키로 중복 데이터를 만들지 않는다.
- 로그에 개인정보, 전체 주소, 비밀값을 남기지 않는다.
